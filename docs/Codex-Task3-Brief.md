# Codex Task 3 Brief — Connection Requests, Consent, Meeting Point, Arrival, Short-Code Connect

*Status: DRAFT, dispatch-ready. Assumes Task 1 (Next.js + TypeScript + Tailwind
scaffold, Prisma schema + SQL migrations with RLS, seed: one demo event, 6 demo
participants, 5 preference questions + 1 goal question, placeholder home page,
`.env.example`) and Task 2 (organiser event creation + QR/code join, guest
session tokens, progressive profile, questionnaire, availability toggle with
~15-minute query-time expiry, open-now list with the §9 sort, screens S1–S3)
are complete as specified. Follow `AGENTS.md` in the repo root; it is binding.
This brief covers engineering phases 3–5 core (frontend/backend + database and
access controls) for the connect half of the product: requests, consent,
meeting-point assignment, arrival, and the short-code fallback.*

---

## Objective

Build the complete consent-and-meet flow, end to end, for real two-user state:

1. A participant taps a person on the open-now list (S3) and sends a
   **connection request** carrying a system-derived **shared reason** and a
   **duration choice (5 or 10 minutes)**.
2. The recipient sees the incoming request and can **Accept** or **Later**.
3. A request that is declined, dismissed, or ignored is **indistinguishable
   from one that simply expired** — in every API response and every UI state
   the requester can see, at every point in time.
4. **Rate limits and block/report basics** are enforced server-side.
5. On mutual accept, a session is created and a **meeting point is assigned**
   (least-crowded of the event's configured points), shown **identically** to
   both sides with photo + one-line direction; both tap **"I'm here"**; when
   both have arrived, the session enters its **started** state.
6. Two people who have already met can connect instantly via a **short code**
   instead of the board.

Screens delivered: S4 (Request Sent + incoming-request view) and S5 (Meet)
per the screen spec — minus the prep card's content, which is Task 4. The
four-card conversation arc itself is NOT part of this task: Task 3 ends at
both-arrived triggering the session start state.

## Scope in

**Send a request (from S3 → S4)**
- `POST /api/connections` — body: target participant, duration choice
  (5 or 10 minutes). Creates a `Request` row with `expiresAt = now + 15
  minutes`. Preconditions checked server-side: caller and target are in the
  same event; target is currently open (Task 2 availability); caller is not
  in an active session; no pending request already exists for this pair in
  this event; the pair is not in cool-down (below); neither has blocked the
  other; the target is under the pending-incoming cap (below). Any failed
  precondition returns the **same neutral "not available right now"
  response** — no reason, no distinguishing detail (see Constraints).
- **Shared reason**, computed server-side at send time and stored on the
  request: exactly one grounded item, derived only from consented structured
  data — the Task 2 chip rule (the verbatim option text of one question both
  answered identically and neither skipped); if none exists, the goal
  relation stated verbatim (same goal: "You're both here to X"; different
  goals: both goal lines, unembellished). No free text from the requester;
  no generated prose. The recipient sees the shared reason and the duration
  before deciding.
- **Simultaneous requests (§10):** if a pending request already exists in the
  opposite direction for this pair, the second send converts it to an
  acceptance instead of creating a duplicate row — a mutual request is
  consent. Both sides proceed to S5 exactly as after an accept.
- S4 per §7: who was asked, the shared reason, the duration, expiry in words
  (~15 min, silent), "they'll get a gentle nudge; no reply just means not
  now." Secondary actions: cancel own request; ask someone else (returns to
  S3). On accept (detected via polling) → S5. On expiry → silent return to
  S3: no notification, no banner naming the outcome, no history entry.

**Receive + respond (incoming-request view)**
- `GET /api/connections` — the caller's own connection state, refreshed by
  **3-second polling**: incoming pending requests (requester display name,
  goal line, shared reason, duration, time remaining) and the caller's
  outgoing request in its requester-facing projection (below). This is the
  only request surface; there is no other list, history, or count.
- `PATCH /api/connections/:id` — actions: `accept` (recipient), `later`
  (recipient dismisses), `cancel` (requester withdraws own pending request).
  Validate that the caller is the correct party for each action.
- **Accept** → creates the `Session`, assigns the meeting point (below),
  clears/pauses both participants' availability (auto-pause after accept,
  §5 #7), mutes new requests for both until the session closes (§5 #18), and
  moves both clients to S5 on their next poll.
- **Later** → removes the request from the recipient's inbox immediately.
  It has **no requester-visible effect at any time**: the requester's
  projection continues to show the request as pending until `expiresAt`,
  then as no longer pending — identical to never having been seen.

**Requester-facing projection (the decline-invisibility rule, implemented)**
- The requester never reads the raw `Request` row. Every requester-facing
  response derives status as: `accepted` if accepted; else `pending` while
  now < `expiresAt`; else `expired`. The recipient's internal outcome
  (accepted / dismissed via Later / never seen) is stored server-side only
  and is never serialised to the requester — no field, no status string, no
  timing difference. Decline is not a stored status visible to anyone
  (Master §8); there is no `declined` value in any response.
- Recipient-side reads of their *own* inbox may show their own actions to
  themselves; nothing about a recipient's action is ever exposed to the
  other party.

**Meeting-point assignment (on accept)**
- Assignment is a **pure, unit-tested function**: inputs are the event's
  configured meeting points (from Task 1 event config: id, label/number,
  photo URL, one-line direction) and the count of live sessions currently
  assigned to each point (sessions created and not closed/cancelled).
  Output: the least-crowded point; ties break by the event's configured
  point order. (No location data exists in this product — see Constraints —
  so configured order is the only "nearest" proxy; do not invent another.)
- The assigned point is stored on the `Session` and returned to **both**
  participants as the **identical object** (same id, label, photo URL,
  direction) in their respective session payloads.

**Arrival + session start (S5)**
- S5 per §7: meeting point number + photo + one-line direction (in words,
  not map-only), partner display name, the chosen duration as the time box,
  waiting-for-partner state. The prep-card slot is present in layout but
  renders nothing in this task (Task 4 fills it). Secondary: "running late"
  (sets a neutral hold flag the partner's S5 shows as "on their way"; the
  point is held).
- `POST /api/sessions/:id/arrive` — the caller marks themselves arrived
  (idempotent). When both participants have arrived → `Session.startedAt`
  is set and the session state becomes `started`. **This is where Task 3
  ends**; Task 4 owns everything from `started` onward.
- `POST /api/sessions/:id/start` — either participant who has arrived may
  start anyway if the partner is late (Master §7 S5: "or either taps
  start"); sets the same `started` state.
- `POST /api/sessions/:id/cancel` — pre-start only: either participant
  cancels before the session starts. The partner's S5 shows the §7 kind
  message and returns them to S3 **with availability restored**; the
  canceller returns to S3 likewise. The meeting point is released. No
  reason is captured or shown, and nothing about the cancellation is
  recorded against either participant anywhere the other can see.
- On accept, both participants are auto-paused (not shown open) and muted
  for new requests until the session closes (close itself is Task 4); a
  pre-start cancel un-mutes and restores availability per above.

**Short-code connect (fallback, §4 Step 3 / §6)**
- Every participant has an event-scoped **short code** (short, typeable,
  shown on their own S3; generated in this task if Task 2 did not provide
  one). It is not a session token and never appears in a URL.
- `POST /api/connections/code` — body: a code. Looks up the code's owner
  within the caller's event only. The owner receives an incoming
  code-connect prompt naming the enterer; the owner taps **Start** (one
  tap — this preserves mutual consent, since a code can be shoulder-surfed)
  → a session is created directly. Because the pair has already met in
  person, **no meeting point is assigned and no arrival step applies**: the
  session enters the `started` state on the owner's tap, with meetingPoint
  recorded as already-together. The enterer's screen waits on the owner's
  tap with the same no-anxiety copy as S4; if the owner dismisses or never
  responds, the code-connect lapses silently under the same
  indistinguishability rule as requests (same TTL).
- Wrong code → plain error + retry, no row created. A code from another
  event resolves to nothing (see Acceptance criteria).

**Rate limits + block/report basics**
- Named, configurable server-side constants (state the values used in the
  PR): `REQUEST_TTL_MIN = 15` (§5 #8 / §10); `MAX_PENDING_INCOMING = 3`
  (§5 #7 — a target at cap is simply not requestable; sends to them return
  the same neutral response as any other unavailability);
  `RE_REQUEST_COOLDOWN_MIN = 30` (brief-set default; §10 requires a
  cool-down after expiry before the same pair can re-request — the constant
  is the deliverable, the number is adjustable); plus a per-participant
  send-rate cap (e.g. `MAX_REQUESTS_PER_HOUR = 20`) returning the same
  neutral response when exceeded.
- One pending request per pair per event, enforced at the data layer as
  well as the API layer.
- `POST /api/blocks` — body: participant. Effect: neither party can send
  the other a request or code-connect for the rest of the event; attempts
  return the same neutral "not available right now" response. The blocked
  party is shown nothing different anywhere. Unblock is not required in
  this task.
- `POST /api/reports` — body: participant, optional category. Stores a
  report row readable only at the organiser/data layer (never by the
  reported participant, never by other participants); the reporter gets a
  generic confirmation. Reporting does not by itself change the reported
  participant's state in this task (organiser removal is a later task).
- A participant in an active session, muted, blocked, at cap, in cool-down,
  or no longer open is uniformly "not available right now" to any sender —
  the response never says which.

**Access control / RLS**
- Every API query scoped by `eventId` + caller session token (hashed
  lookup), as in Task 2.
- RLS policies (extending Task 1/2 migrations if needed) so that, at the
  database level as well as the API level: a participant can read only
  their own requests (as sender, in the projection; as recipient, their
  inbox) and their own sessions; a session is readable only by its two
  participants; blocks and reports are readable by no participant (report
  rows: organiser/data layer only); nobody can read another participant's
  request history (Master §8).
- All API inputs validated server-side (types, lengths, enum membership —
  duration is exactly 5 or 10; event-active and same-event checks).

**Docs**
- README: final API contract for every route implemented or adapted in this
  task (method, path, auth = session token header, request/response shapes),
  explicitly noting that `GET /api/connections`, `POST /api/connections/code`,
  `POST /api/sessions/:id/arrive`, `POST /api/sessions/:id/start`,
  `POST /api/sessions/:id/cancel`, `POST /api/blocks`, and
  `POST /api/reports` are adaptations/additions beyond the engineering
  prompt's list, and that `/api/recommendations`, `/api/icebreaker`, and
  `/api/feedback` are not yet implemented.

## Constraints

The following are quoted verbatim from `AGENTS.md` and are binding on this
task. Violating one fails review.

> 1. **Never display** compatibility scores, percentages, rankings, vote/match counts,
>    or popularity metrics anywhere in UI or API responses to clients.
>    `recommendations.score_internal` must never leave the server.
>    *(In this task: no count of incoming/outgoing requests is displayed or
>    sent as a metric or badge; the inbox is a list, not a number.)*

> 2. **Rejection is never visible.** A declined or ignored connection request must be
>    indistinguishable from an expired one for the requester — same UI, same timing,
>    no status they can read. There is no "declined" state exposed to senders.
>    *(This law is the core of this task. It binds payloads AND timing: a
>    recipient's Later must produce no requester-visible change before

>    never-seen. See the projection rule under Scope in.)*

> 3. **Grounded content only.** Conversation cards/prompts may use only structured,
>    consented data, presented verbatim. Never fabricate a shared interest, never
>    paraphrase a user's profile into an inference ("seems introverted" is banned —
>    no code path may generate evaluations of a person).
>    *(In this task: the shared reason is the verbatim chip text or the
>    verbatim goal relation, computed from both participants' actual data.
>    There is no requester-written message field, and no code path may
>    generate any other text about a person.)*

> 6. **Event-scoped, expiring data.** Every query is scoped by event + the caller's

>    conversation and then gets out of the way (phones face-down between cards).

Task-specific constraints:
- The requester-facing status is a **derived projection** (accepted /
  pending-until-`expiresAt` / expired), computed at read time from the
  stored row. The raw request row — including the recipient's internal
  outcome — is never serialised to the requester.
- Request expiry is a query-time computation against `expiresAt` (Master
  §8); no cron jobs, scheduled functions, or client-side-only expiry (the
  client countdown is display only — the server decides).
- Every unavailability is the **same neutral response**: target not open,
  at cap, in a session, muted, blocked (either direction), pair in
  cool-down, duplicate pending, or sender rate-limited — one response
  shape, no reason codes the client can distinguish.
- Meeting-point assignment uses **no location data**: GPS/continuous
  location is excluded by the product spec (Master §6), none exists in the
  data model, and none may be collected for this task. "Nearest" is
  realised solely as the configured-order tie-break in the assignment
  function; least-crowded is the primary key.
- Both participants' S5 payloads carry the **identical** meeting-point
  object from the single assignment stored on the session — never two
  independently computed copies.
- Copy honesty: waiting and lapse copy never names an outcome ("declined",
  "ignored", "rejected" are banned words in requester-facing UI and API
  strings); S4 copy follows §7 ("no reply just means not now").

## Acceptance criteria

All criteria are testable; run them and report actual results (AGENTS.md
testing-honesty rule).

**Sending a request**
1. `POST /api/connections` with a valid open target and duration 5 or 10
   creates exactly one pending request with `expiresAt ≈ now + 15 min`;
   the recipient's next `GET /api/connections` poll shows it with the
   requester's display name, goal line, the shared reason, and the
   duration. A duration other than 5/10 is rejected with a clean 4xx.
2. The stored shared reason equals the verbatim option text of a question
   both participants answered identically and neither skipped (seed a pair
   with a known shared answer and assert the exact string); for a pair with
   no shared non-skipped answer, it equals the verbatim goal relation.
   No requester-supplied text exists anywhere in the payload.
3. Duplicate send while a request for the pair is pending creates no second
   row. Simultaneous opposite-direction sends resolve to a single accepted
   request + session (the §10 mutual-request rule), with both clients
   landing on S5.

**Decline invisibility (required)**
4. **Indistinguishability test:** script three scenarios against the same
   seeded pair setup — (a) recipient taps Later immediately; (b) recipient
   never opens the inbox and the request lapses; (c) recipient opens but
   takes no action and the request lapses. At matched time points (before
   expiry, at expiry, after expiry), capture the requester's
   `GET /api/connections` responses and S4/S3 UI states in all three
   scenarios and assert they are **identical** — same fields, same status
   strings, same shapes. In particular: scenario (a) shows `pending` until
   `expiresAt` exactly as (b) and (c) do, and no response in any scenario
   contains a `declined`/`dismissed`/`rejected` status or field.
5. After any of the three scenarios, the target (if still open) still
   appears in the requester's open-now list exactly as before, and no
   history, record, or count of the lapsed request is visible to the
   requester anywhere in UI or payloads.

**Accept → meeting point → arrival (required end-to-end)**
6. **Two-session end-to-end test (required):** two independent sessions
   (separate browser contexts or two token clients) in the same event.
   A sends a request → B accepts → both clients' next polls show S5 with
   the **identical** meeting-point object (assert deep equality of id,
   label, photo URL, direction across the two payloads) and the chosen
   duration as the time box. A taps "I'm here" → A's S5 shows
   waiting-for-partner; B taps "I'm here" → the session state becomes
   `started` with `startedAt` set, visible to both. Refresh/close/reopen
   at the waiting, S5, and arrival steps each restores the exact state
   from the token.
7. **Assignment test:** the assignment function is a pure function with
   unit tests covering: emptiest point wins; tie breaks by configured
   order; a point's live-session count increments on assignment and is
   released by a pre-start cancel. With seeded sessions occupying the
   first configured point, a new accept is assigned the next point.
8. On accept, both participants disappear from other participants'
   open-now lists (auto-paused) and sends addressed to either return the

**Short-code connect**

    no arrival step; B's waiting screen resolves to the same started
    state. If A dismisses or never responds, B's experience is identical
    to a lapsed request (criterion 4's rule, same TTL).
11. A wrong code shows the plain error and creates no row; a valid code
    from a different event resolves to nothing (no prompt, no row).

**Rate limits, block, report**
12. With 3 pending incoming requests seeded for target T, a fourth send to
    T returns the neutral response and creates no row; after one of the
    three lapses, a send to T succeeds. Sends to a target who is closed,
    in-session, muted, blocked, or in pair cool-down each return the
    **identical** neutral response (assert response equality across all
    causes).
13. After A lets B's request lapse, B's immediate re-send to A returns the
    neutral response (cool-down); after the configured cool-down, a
    re-send succeeds. State the constant used.
14. After A blocks B: B's request and code-connect attempts to A return
    the neutral response, A's attempts to B likewise, and B's UI/payloads

**RLS / access control**
